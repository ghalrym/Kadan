# Workspace file delivery

`save_workspace_file` is a conversation tool because the run owns its destination and durable action identity. `RunConversation` derives the asset ID from the persisted command position, supplies the current agent namespace, and checks ownership before downloading and immediately before uploading. Transfers do not hold the runner mutation lock, allowing lease renewal while bytes move. Cancellation after the upload starts cannot revoke a committed file.

`SandboxClient.download_file` streams the pinned sandbox's `/v1/file/download` response into a caller-owned temporary file with `change_policy=abort`. It bounds chunks, total time and bytes, hashes the complete download, and rejects failed, partial or length-mismatched responses. The limit is 100 MiB. The pinned sandbox contract promises raw bytes and source-change abortion but does not promise a length header; midstream change detection ultimately depends on that service. Temporary files and HTTP responses are closed on errors and cancellation.

`WorkspaceFiles` posts the seekable file as multipart data through Tsuchi's existing asset upload. Tsuchi independently limits, hashes and classifies the bytes. Kadan checks the returned namespace, ID, filename, size, hash and active state before confirming the save. The source basename becomes display metadata; it is not a storage path. No schema or storage endpoint changes are needed.

After a restart, the same command reads its deterministic asset ID. It can confirm an existing active record without rereading the source. Missing, trashed or unavailable records produce uncertainty rather than another upload. `read_workspace_file` lets the agent check an uncertain outcome later and returns metadata plus the existing Kadan asset-download URL; it does not expose file contents to the text model. A new command has a new action ID and therefore creates a separate copy.

The pinned API contract is documented in the [sandbox 1.11.0 OpenAPI](https://github.com/agent-infra/sandbox/blob/v1.11.0/website/docs/public/v1/openapi.json). Existing sandbox authorization is reused. The shared computer remains shared; the agent namespace scopes the stored destination, not its source filesystem. See [File delivery expectations](../../user-expectations/kadan/file-delivery.md).

## Opening a stored file

`open_workspace_file(file_id)` uses the running agent's namespace to read active Tsuchi asset metadata. `WorkspaceFiles.open` streams its bytes into a temporary file, bounds size and time, and verifies the immutable size and SHA-256 before any computer write. `SandboxClient.upload_file` posts that seekable stream as multipart `file` and `path` to `/v1/file/upload`. The pinned API returns an outer success envelope containing `file_path`, `file_size` and another success flag; HTTP 200 alone is not confirmation. The client validates both flags and the destination/size, then the coordinator independently downloads the resulting file and checks its size and hash. A lost upload receipt can be reconciled by this readback without another upload.

The destination is a command-derived absolute path under `/tmp`, with a bounded display filename. Tools cannot supply another agent namespace or choose an existing destination. Kadan checks a destination before writing, reuses an identical copy and refuses a different one. The sandbox API does not expose exclusive creation, so this check does not exclude an unrelated computer writer racing the initial upload. The shared computer provides no per-agent filesystem isolation. Ownership is checked before reading and immediately before uploading, without holding the runner mutation lock across transfers.

Replay reads the same destination and compares it against active source metadata. A missing, changed or unavailable copy is reported as uncertain and never re-uploaded. A new command gets another path; local edits are never synchronized back to Tsuchi. Copying returns a path rather than adding bytes to model context. These are temporary computer inputs, not another durable file store. See [Opening Workspace files](../../user-expectations/kadan/opening-workspace-files.md).

## Discovering stored files

`list_workspace_files(query="", limit=20, offset=0)` is a read-only conversation tool scoped to the run's agent. It accepts limits from 1 to 50, nonnegative offsets and an optional query of at most 500 characters. An omitted or blank query lists all active files. It calls the existing Tsuchi asset query with `trash=false`, requesting one extra match to determine continuation. No file bytes or computer calls are involved.

Tsuchi owns [metadata matching and pagination](../tsuchi/file-queries.md). Kadan uses that stable ordering without deduplicating display names. A late page or no matches can still scan the collection.

The tool returns `files` and `next_offset`. Each file includes `file_id`, title, filename, media type, byte size, checksum, metadata version, created/updated timestamps and its download URL. Names are display metadata and never deduplicated. A non-null `next_offset` continues with the same query and limit; an empty list with null continuation is a successful no-match result. Pages are separate reads, not a snapshot, so concurrent edits can shift offsets. Kadan validates every returned row, including the lookahead, for active same-agent metadata and rejects malformed, oversized or duplicate-ID lists without returning partial results. Storage failures produce a tool error without `files` or continuation. The existing read/open tools recheck current metadata by the selected stable ID.

The additional tool schema counts against the existing context budget. The complete conversation-tool set exceeds the allowance for a 4,096-token context after the reply reserve, so such a window is rejected before inference. Discovery does not relax admission or automatically change model settings.
