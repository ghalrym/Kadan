# Memory tools and hybrid memory architecture

The runner supplies the agent namespace to `AgentMemories`; tool arguments cannot change it. List and ordinary read operations expose active memory resources only. `read_memory` accepts `include_trashed` for checking uncertain writes; a trashed result includes identity, title, version and deletion time without Markdown or tags. Writes reject other resource kinds, other namespaces and mismatched resource IDs. See the user expectations for [agent memory](../../user-expectations/kadan/memories.md) and [forgetting memories](../../user-expectations/kadan/forgetting-memories.md).

`update_memory` and `forget_memory` accept an optional `expected_version`. When `expected_version` is omitted (`None`), `AgentMemories` reads the active record's current version internally before checking ownership and issuing the versioned Tsuchi write, enabling single-call edits without sacrificing run-lease fencing. Passing an explicit `expected_version` enforces strict optimistic version conflict checking before and inside Tsuchi's write transaction. `forget_memory` calls Tsuchi's resource `DELETE` with `expected_version` in the query, preserving the record and revision history and requiring confirmation of a matching memory with a deletion time and incremented version.

Every memory mutation checks run ownership immediately before its storage request, after any preflight read. Cancellation or lease loss after the request starts cannot undo a committed change. Recovery repeats reads but returns uncertainty instead of replaying writes; the agent must inspect the current record before deciding what to do next. An unknown outcome is not a confirmation of success or failure.

## KV-cache-safe hybrid memory injection

Kadan combines epoch-frozen Core Memories with append-only tail archival recall (`kadan/api/memory_context.py`) so Hikari's exact-prefix KV cache stays hot across turns within a compaction epoch:

1. **Core Memories selection:** Active Tsuchi memories tagged `"core"` (case-insensitive), or up to 5 most recent active memories when an agent has at most 5 active memories and none are tagged `"core"` yet. Formatting caps output to at most 12 entries and ~2,500 characters.
2. **Epoch-frozen `system` snapshot:** Each Tsuchi conversation stores `core_memories_snapshot` and `core_memories_refreshed_at`. During `AgentRuns.context`, when `core_memories_snapshot` is `None`, the runner builds it from current Tsuchi core memories and persists it via `PUT /api/agents/{key}/resources/{id}/memory-state` with `only_if_snapshot_unset=true`. On subsequent turns in the same epoch, the persisted snapshot is reused verbatim (after the persona, before `compacted_summary`) so the `system` prompt stays byte-identical.
3. **Refresh and invalidation boundaries:** Both 30-minute idle compaction (`IdleCompactor`) and in-run budget compaction refresh `core_memories_snapshot` atomically alongside `compacted_summary` via `PUT /compaction`. Direct user memory edits in Kadan or Tsuchi clear `core_memories_snapshot` to `None` on the agent's active conversations so corrections take effect on the next turn; background extraction passes `preserve_memory_snapshot=true` so mid-epoch extraction never invalidates the live chat KV cache.
4. **Append-only tail archival recall:** On user-triggered runs, the runner extracts distinctive search terms from the triggering user message (filtering stop words and greetings) and searches active non-core memories (excluding IDs already in Core Memories). Top matches (up to 3 entries, ~1,500 characters) are appended at the tail of the turn context as an ephemeral `recalled_memories` observation (never in `system`), keeping prior turns' KV prefix intact.

## Decision-gated background extraction (`MemoryQueue`)

`kadan-runner` runs `MemoryQueue` (`kadan/runner/memory_queue.py`) alongside `IdleCompactor`. Completed agent runs signal `memory_queue.wakeup` immediately, and a periodic poll (~25s) catches unprocessed turns after restarts. Any agent or conversation with an active run is skipped.

For each conversation with new user/assistant messages after `memory_extracted_through_message_id`:

1. **Fast decision gate:** Evaluates up to three `Noul` questions (`should_save_memory`, `is_core_memory`, and `should_update_persona`) via Hikari `POST /v1/decisions` when local Inkling 2 Mini is active, or via a lightweight `reuse_prefix=False` structured-JSON fallback when a cloud subscription handles language.
2. **Zero-generation fast path:** If actionable gates score below `0.55`, `MemoryQueue` advances `memory_extracted_through_message_id` in place with zero LLM generation tokens spent.
3. **Compact background extraction:** If gated yes, `MemoryQueue` runs one `priority="background"`, `reuse_prefix=False`, `conversation_key=None` structured-JSON call with the new turn slice, existing memory summaries for deduplication/in-place updates, and current persona Markdown when persona updates are gated yes. Writes pass `preserve_memory_snapshot=true`, fill answered onboarding `TODO`s when needed, and advance `memory_extracted_through_message_id` durably without mutating an already-set `core_memories_snapshot`.
