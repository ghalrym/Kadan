# Image upload settlement

Tsuchi owns the saved outcome of Kadan's generated-image uploads. Each image job stores `upload_status`, defaulting to `not_started` in existing JSON records. The owning Kadan worker can change it to `pending` through the usual version-checked job update before sending bytes. Only storage can settle it as `completed` or `failed`; workers cannot reset it. The job remains active while the outcome is pending.

Generated asset uploads include `image_job_id` and the reserved asset ID, `uuid5(job.id, "image")`. `FileStorage.upload` holds an exclusive per-job file lock throughout byte ingestion, immutable blob publication and asset registration. Asset metadata and the completed upload outcome commit in the same repository transaction. This storage operation can finish after a Kadan timeout, Stop request or ownership change. Registering bytes does not itself complete the job or enqueue a conversation event.

`POST /api/agents/{key}/image-jobs/{job_id}/upload/resolve` attempts the same lock without waiting. A busy lock leaves the outcome pending even if metadata is absent. Once acquired, storage can close a pending upload as failed: no writer is still inside the upload, and delayed requests must check the persisted gate before writing. A process exit releases its locks, so recovery after a Tsuchi restart can close abandoned uploads without using lease age or sleeps as evidence. Lock files retain their inodes across restarts and replays; they must not be unlinked while services use the storage directory.

Upload errors close the gate while holding the lock. Database errors that prevent confirmation leave the persisted outcome recoverable. As with other immutable uploads, a crash after blob publication but before registration can leave unregistered bytes; settlement can close that upload without registering those bytes later. Confirmed upload outcomes cannot be downgraded by cleanup or stale worker updates. Identical asset registration replays reuse the existing asset; conflicting artwork and recreation of missing metadata after confirmed completion are rejected.

Kadan owns final validation, job completion and cancellation. Tsuchi retains the existing atomic terminal event and delivery receipts, so repeated settlement does not create another wake-up event or deliver the image twice.
