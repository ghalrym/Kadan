# BF16 application diagnostic v1 — proposed, not executed

This is a separately versioned diagnostic protocol for the actual application
precision. It does not repair, supersede or pass the failed FP32/eager and
FP32/oracle gates. Original eager's later-block oracle failures and the rejected
controlled-accumulation candidate v1 remain recorded. No GPU execution or service
interruption is authorized by this document. Independent review is required
before implementation/execution; the existing launcher and stopped ladder remain
unchanged, with no bypass flag.

The machine-readable specification is `bf16-application-protocol-v1.json`.
Review both files as one protocol. Subsequent changes to cases, arithmetic,
criteria or scope require a new version before evaluating affected cases.

## Staged comparisons

1. Capture the pinned eager path and verify complete artifact identity and shapes.
   Replay eager against its capture at the same BF16 criterion below. A mismatched
   baseline blocks interpretation of parallel results.
2. Verify bit-exact fused sequence/head exchange and inverse at the actual shape,
   including row/head order and compact prefix ownership. This is a separate
   transport check, not a numerical-fidelity pass.
3. For each block 0–31, reset eager and Ulysses to the exact same captured incoming
   hidden state and constants. Compare eager replay with capture and Ulysses with
   both eager replay and capture. These teacher-forced comparisons isolate local
   full-length BF16 differences. Report every block/rank, not only a mean.
4. Run paired chains of 1, 4 and 32 blocks starting from block 0's captured input.
   Eager advances its own output into the next block; Ulysses advances its own
   output. Never replace either chain's intermediate state with captured hidden
   states. Use the same per-block conditioning/prefix/RoPE/mask. Compare each
   constituent block output against the paired advancing eager chain; separately
   check eager reproducibility against the captured chain.
5. For the 32-block chain, apply the unchanged final adaptive norm and output
   projection and compare full denoiser predictions. Include all target rows,
   remove only declared partition padding, and gather in original global order.

No speed benchmark follows automatically. Only after all cases pass may a
separately reviewed timing run measure actual distributed latency; diagnostic
CPU audits and capture/disk reads must be outside its timed region.

## Frozen acceptance and reporting

Retain the already declared BF16 criterion exactly:
`abs(actual-reference) <= 0.02 + 0.02 * abs(reference)` for **every element**,
with zero violations and zero NaN/Inf. Apply the same criterion at every block
output in teacher-forced tests and accumulated chains and at the final norm/
projection output. No relaxed chain threshold, allowed-outlier quota, percentile
replacement, selected-coordinate exemption or accumulated-drift allowance.
These are the existing BF16 block/chain checkpoints. Internal projection, norm,
attention and residual operator values remain diagnostic only.

Stream CPU FP64 comparisons over bounded chunks of stored BF16 values. Preserve
per-rank and global violation/nonfinite counts, maximum normalized error with
coordinate/reference/actual/bound, largest absolute error, RMSE, relative L2,
and error quantiles. Aggregate counts by sum and extrema by maximum, never by
averaging ranks to hide a violation. Quantiles and relative metrics do not create
new acceptance limits. If listed coordinates are truncated, preserve the full
count and bounded output artifacts for inspection and say truncation occurred.

Persist each result before rank-wide acceptance/stop. Any numerical or identity
failure stops the case and later execution until review. Earlier successful
stages remain individually reported; unrun/time-limited/missing stages are not
passes. The aggregate outcome can be only `passed-declared-bf16-diagnostic-scope`,
`failed`, or `incomplete`; it must always retain a separate `fp32_protocol=failed`.
Even a complete pass does not imply full scheduler, image or production readiness.

## Resources, ownership and restoration

Run one declared case per coordinated maintenance window. Reuse the established
absolute 2100-second pause budget from before API stop, including 600 seconds
reserved for exact restoration. Each stage has at most 900 seconds, clipped by
remaining measurement time with cleanup margin. Readiness cannot start a fresh
clock. Timeout means incomplete/failed execution and immediate cleanup/restoration,
not lower resolution, fewer rows, or silently omitted checks.

Keep the existing single inference-lock inode, idle-queue admission, desktop PID/
starttime baseline, unknown-owner rejection and fail-stop supervision. Hold both
GPU reservations and the lock until all ranks/process groups are reaped. Verify
physical memory recovery; unconfirmed cleanup quarantines the GPUs. Restart only
the exact captured API container, verify unchanged source/config/mount identity,
health and native small-model readiness; never recreate unrelated containers.
No DB mock data, production orchestration changes, UI changes or image rebuilds.

Per case: 128 GiB host RAM/no swap, four CPUs, 1 GiB shared memory, 22 GiB allocator
limit per GPU, 32 GiB capture ceiling, 120-second collective timeouts. Admission
requires 160 GiB available host RAM and 22 GiB physical free per card after the
coordinated stop. Retain existing thermal/free-memory guards. Count contexts,
NCCL, prefix replicas, packed buffers, CPU file cache and physical GPU usage;
allocator accounting alone is insufficient.

**Aggregate storage change requiring review:** retaining three separate case
captures permits up to 96 GiB of new evidence, with 128 GiB initial free disk
headroom. Each case still stops at 32 GiB, including partial files. Preserve all
historical captures; no deletion to make a failed run fit. Disk remains bounded
slow artifact storage. Separate windows prevent extending a live pause to cover
three cases; every window must independently pass admission and restore checks.

## Review submission and remaining work

This commit contains the protocol only, not an executable BF16 bypass. Reviewers
should explicitly assess baseline fidelity, held-out cases, unchanged criteria,
chain semantics, artifact binding, the increased aggregate disk cap and pause/
cleanup controls. Implementation then needs its own source review and exact-head
green CI before any coordinated execution. The review record must name the exact
protocol/source commits; a plan document or successful CPU test is not execution
approval.

After this scope passes, a later version must cover selected additional timesteps,
full free-running scheduler trajectories and decoded image comparison. Editing,
reference-image and other aspect-ratio cases also remain outside this protocol.
The failed FP32 evidence and rejected candidate v1 remain visible regardless of
later BF16 results.
