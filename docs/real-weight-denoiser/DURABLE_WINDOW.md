# Durable image-A review window

This proposal is not execution approval. It is stacked on the transport-policy
review so host and rank transport use the same verified 85/90 C policy. The main
checkout and running API are not changed by creating a review commit or bundle.

## One clock, separate recovery

`local_evidence_run.py` writes and fsyncs `window.json` before submitting the user
service. The same monotonic start governs preflight, work and restoration. The
boot ID prevents reuse across reboot. Activation after 15 seconds is rejected
before starting the operator. Work ends at start+900 seconds; the operator's
cleanup limit is start+1350; the entire window ends at start+1800. No stage resets
that total clock. This replaces the earlier 600-second recovery proposal with a
900-second reserve to cover both a stuck supervisor and independent restoration.

The service runs `window_supervisor.py`, with RuntimeMaxSec=900,
TimeoutStopSec=450, KillMode=mixed and Restart=no. The supervisor sends TERM once
and allows up to 300 seconds for operator cleanup, then kills/reaps its process
group. Docker workloads are outside this cgroup: systemd ExecStopPost separately
runs recovery even after the supervisor is killed. It removes only the container
carrying this window's random ownership label, confirms disappearance, checks
physical owners, then starts only the captured original API ID with unchanged
configuration/source. It waits for HTTP health, lifecycle ready and Docker health.
It checks the other captured service IDs and records success only afterward.

Even a supervisor killed at activation+900+450 leaves at least 435 seconds before
the absolute end, allowing bounded metadata reads, Docker removal (15), physical
release (30), original start (45), readiness (180), and final verification.
All subprocess/network timeouts are clipped to the absolute deadline. Repeated
TERM/INT do not raise during recovery. Host death, unavailable Docker, stuck kernel
I/O or persistent GPU ownership cannot guarantee recovery; failures are recorded
as failures/quarantine, never as successful restoration. A manual SIGKILL of the
recovery process itself is outside the recovery guarantee.

## Evidence and exact binding

`reviewed_image_a.py` is the complete proposed operator; `operator.diff` gives
its entire delta against the preserved image-a-ff-preparation operator. The
operator requires source_commit and protocol in binding.json, matching wrapper
and runtime SHA256s, exact-head CI, a clean matching checkout and a separate
single-api-image-a-v2 approval naming the binding SHA256. Old approvals fail.
The bundle contains the exact committed operator as queue_image_a.py and the
committed reviewed_logging.json as logging.json. binding.json is generated after
the commit, avoiding a self-referential commit hash. It pins every tracked API and
harness Python file, payload, predecessor manifest and retained-roots inventory.
No approval record is generated by preparation.

Before stopping the original API, the operator fsyncs recovery.json with the
original ID, configuration digest, source commit, other service IDs and physical
owner identities. It never stores secret-containing Docker environment values.
Request admission/response receipts and selected image progress/timing/publication
events are appended and fsynced during execution to bounded host files. The
logging handler lives on a read-only tools bind; evidence uses a separate writable
bind. Existing thermal evidence/watchdogs remain enabled. The final Docker-log
export is supplementary; it is not the only durable event source.

Future explicitly approved invocation (not executed by this review):

```
KADAN_REVIEWED_QUEUE_COMMIT=<exact-reviewed-head> python3 \
  docs/real-weight-denoiser/local_evidence_run.py \
  --unit kadan-reviewed-<unique-id> --output <new-existing-window-directory> -- \
  /usr/bin/python3 <bound-bundle>/queue_image_a.py a <separate-approval.json>
```

The context directory must be new and not reused. The workload evidence directory
is also exclusive. Runtime source must be the clean exact reviewed commit; this
proposal deliberately cannot run from the currently untouched live checkout.

## CPU validation

`python -m unittest discover -s docs/real-weight-denoiser -p 'test_*.py' -v`
is already part of API CI. Targeted window/evidence tests exercise shared clocks,
75/180-second restoration, stuck operators, independent Docker cleanup after
supervisor timeout, manual stops, repeated signals, foreign ownership, changed
source/configuration, failed physical release, timeout clipping, durable error
receipts, bounded append and producer death. Tests use synthetic Docker operations
and CPU subprocesses; they do not launch Docker workloads or execute GPU work.
