# Experimental LFM3 audio calls

This is an unmerged draft proposal for Hikari and Kadan, available only on the explicitly enabled trial branch. The behavior below describes the intended trial experience, not capabilities accepted on master. Owner manual acceptance is required before merging: human microphone capture, listening and audible quality, real playback acknowledgements, audible barge-in/full-duplex usability, and maximum-context memory fit remain unverified. Historical generated-audio fixtures and unit tests do not satisfy that gate.

An optional trial lets applications explicitly choose LFM3-Audio-2B for a call. The regular call path remains available. The trial is disabled by default and requires the operator to enable its worker and API support. Users must review its model license and confirm its download through Hikari before starting. Opening a call does not accept licenses or download the model.

The trial uses the existing call connection, interruption and playback acknowledgements. It recognizes each completed English utterance, then generates a reply with both text and speech. Each whole reply is buffered as one audio segment before delivery. An operator can separately enable a trial that reuses one loaded executor for recognition and the reply within an utterance, reducing repeated startup work. It keeps the same transcript, interruption and history behavior; a recognized utterance remains in the call even when its reply later fails or is interrupted. Its actual latency still requires comparison on the test machine. Speaking interrupts that turn, and only a fully played, acknowledged reply is retained in the next turn's context. Calls keep the same bounded recent history and discard it on disconnect.

This adapter does not expose live transcription, incremental speech playback, tools, voice cloning or simultaneous listening and generation inside the model. Its voice is generated by LFM3 rather than the regular Ryan voice. It does not promise full duplex inference, response latency, quality or physical memory fit. The BF16 runtime and actual calls require manual validation on the target GPU; unit tests do not establish those capabilities. Missing worker support, unavailable checkpoints, oversized context and incomplete model outputs produce errors rather than falling back to another model.

See [ordinary voice calls](voice-calls.md) for the call lifecycle and [trial architecture](../../architecture/hikari/worker-lfm3-audio.md) for setup and validation.

An additional optional sentence-synthesis candidate first completes a public text answer, then generates bounded speech segments for that known text. Its first completed segment carries the full answer text, and later segments can arrive while playback continues. Only fully played segments are kept after interruption. A later synthesis failure can leave a partial reply already heard. Completion, privacy and audio-format checks do not establish factual correctness or pronunciation quality; those still require review. This candidate is disabled by default and has no promised latency improvement.

Experimental text output can use the model context remaining after the complete prompt; it has no separate short-token or character ceiling. Calls still bound utterances to twenty seconds and generated speech to sixty seconds per turn. Requests exceeding speech duration or physical/transport capacity fail explicitly rather than returning truncated speech. Recent call history retains whole messages; if it no longer fits, start a new call. A model's full context is not a promise that a maximum-size request will fit or run quickly.
