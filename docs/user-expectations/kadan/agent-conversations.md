# Agent conversations

Kadan lets users hatch an agent and talk with it in one ever-persistent chat thread. Creating an agent saves its records in Tsuchi without downloading or running a model. Users can [rename agents](renaming-agents.md); deleting agents is not available.

Hatching requires a name and a unique permanent key. Invalid or duplicate keys produce an error without replacing an existing agent. After an uncertain creation, refresh the agent list before trying again. Kadan opens the first agent returned by Tsuchi after refreshing; other existing agents are not selectable in Kadan. Both applications use the same [namespaces](../tsuchi/namespaces.md).

## Single persistent chat

Each agent has one ever-persistent conversation thread stored in Tsuchi. Kadan opens that thread automatically when it loads, creating it on first use. Whenever more than 30 minutes pass between messages (including when you return and send a new message after being inactive for over 30 minutes), Kadan draws a timestamp divider bar across the chat (`--- XX:XX am/pm ---`) so the elapsed time is clear.

The thread handles context compaction automatically so users never need to start new chats or manually compact. After more than 30 minutes of inactivity, the server auto-compacts older messages into a durable rolling summary in the background while keeping all earlier messages intact in saved history. During long active sessions, Kadan also compacts older messages automatically as the thread approaches the model's context budget, keeping the most recent messages verbatim and preserving all saved history.

One unsent draft is kept per agent in the current browser tab; it can be lost when the tab closes and is not a saved message. When refresh opens a different agent, Kadan waits for that agent’s thread rather than showing the previous agent’s. If loading fails, it reports the error; retry refreshes the records. A failed refresh for the same agent leaves its last loaded chat visible.

Users can [upload files and attach them](chat-attachments.md) to a message or note. When the user mentions saved documents or memories, the agent uses its tools to find and read them. Upload confirmation is separate from message delivery. Sending saves the message and queues work. Users can keep typing and send more messages while earlier work waits. Replies can be delayed by other work or model loading. The agent can finish work without sending a visible reply; stopped work remains visible. When an error interrupts a response, Kadan retries up to three times automatically; if the response still cannot be completed, the agent replies in chat letting the user know it struggled to complete the task without sharing exact error details unless the user asks for details. Failed responses are never shown as error notices in the chat interface.

Each queued reply receives the conversation through the message that requested it. Kadan preserves the text people and agents wrote, including indentation. Message identifiers and attached file references stay separate from that text. Background updates are identified as results from the service that produced them. Earlier saved replies retain their original wording and can be edited in Tsuchi’s Conversations view. If Kadan cannot identify an action in an older saved response after an upgrade, it stops before repeating any work and lets the user know it struggled to complete the task. Messages already delivered remain available.

The standard deployment uses Inkling 2 Mini for text conversations (or the subscription selected for Language in Hikari Settings). Its checkpoint must be downloaded through Hikari Settings first when using Local; an unavailable worker or incomplete download never switches models. A completed plain answer becomes an agent reply when the agent is permitted to reply. Empty output can still finish silently. Malformed tool output or multiple actions in a single step are never executed or shown raw; Kadan retries up to three times before having the agent respond that it struggled to complete the task.

**Sending…** means a message or note is awaiting save confirmation. **Delivered** means it was saved in the conversation; it does not confirm that the model has read it. A later reply may come from earlier work.

While response work is pending, Kadan shows whether it is queued or waiting for a response. When Hikari reports a language-model download or load, Kadan shows that state. As the agent writes a direct reply, Kadan can show the reply live as text arrives before the final message is saved; this live preview is temporary and clears if the agent takes another action instead of replying, or is replaced by the saved reply once delivered. These indicators refresh periodically and can lag changes. A loaded model does not prove that this prompt is being processed: Kadan does not currently receive that stage, so it shows no prompt-processing claim or estimated percentage. Downloads remain explicit actions in Hikari Settings; a progress label does not start or retry work.

Saved history survives navigation and service recovery. **Show earlier messages** reveals older messages. [Find in conversation](finding-chat-text.md) searches saved text, and [reading controls](reading-chat.md) let users keep their place as replies arrive. Only a limited recent portion is included automatically in each response; the agent can [search and read older delivered chat](conversation-history.md) when needed. Image generation can deliver a result later in the same chat.

Users can [download the saved chat as Markdown](downloading-chat.md), including older saved messages without revealing them first.

Each response has a limit of 24 commands and a bounded context for instructions, recent messages and action results. Reaching either limit stops further work and has the agent reply that it struggled to complete the task rather than continuing indefinitely. Saved history and messages already delivered remain. Sending a new message starts new work and does not guarantee completion of the earlier task. A saved message can also wait for [runner availability](runner-availability.md).

The agent reasons privately before each step; its reasoning is never shown or saved. Kadan limits private reasoning and reply generation separately so reasoning cannot continue indefinitely. Kadan leaves estimated space for both budgets when selecting recent history and checking saved work. Instructions and tool definitions still have to fit; insufficient space prevents inference and causes the agent to reply that it struggled to complete the task. These budgets do not guarantee a fixed response time or that every command within the command-size limit will fit. If Hikari reaches the generation or context limit before completing an agent response, Kadan does not execute a command from the incomplete response, retries up to three times for output-limit errors, and otherwise has the agent respond that it struggled to complete the task. Actions completed earlier in the run remain completed.

After a send error, **Reload** checks what was saved. **Retry** under **Unsent message** keeps the original submission and attachment list. Resolve or discard it before sending another message. Closing the tab does not cancel saved work; use [Stopping chat work](stopping-chat-work.md).

Trashing or restoring conversations in Tsuchi can change which chat opens after refreshing Kadan. Unsent submissions remain with their original conversation in the current browser tab and reappear if that conversation is reopened. The agent's ordinary draft remains available across this change.

An **Earlier unsent message** has no recorded conversation and cannot be retried safely. Its text remains available to copy into the current draft or discard. Copying preserves existing draft text and does not send anything. Check saved history before submitting it again to avoid a duplicate.

See [Conversation architecture](../../architecture/kadan/agent-conversations.md) for ownership, context and recovery.
