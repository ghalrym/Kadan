Profiling method and synchronization interpretation
profiling/cuda_phase_profile.cpp is the measured LD_PRELOAD CUDA13 interposer.
It surrounds __cudaLaunchKernel with CUDA events; host callsite offsets resolve
against `nm -n -C WORKER` using profiling/summarize_profile.py. SIGUSR1 marks a
phase boundary; send it while the worker awaits its next pipe command, after
ready and after the final prompt reply. The next launch snapshots/resets counters.
Phase 0 contains loading; phase 1 prompt; phase 2 decode. Generated EOS is included
in native-step phase counters but excluded from API decode-rate reporting.
Library build: g++ -O2 -shared -fPIC cuda_phase_profile.cpp -o phase_profile.so -ldl
with CUDA runtime headers. Preload ONLY in the worker, not the API process.
Raw phase aggregates, workload, token IDs and API records: profiling/20261008-results.json.

Matched router-only decode: 149 steps, 181.779 ms GPU events/step;
5.178 ms host launch calls/step; 6.536 ms D2H calls/step. About 1095 stream-sync
calls/step (~27 per layer). Their 175.47 ms wait/step INCLUDES GPU execution;
do not add this to kernel time or call it exclusive synchronization overhead.
After attention: 150.525 ms GPU events/step, 5.272 ms launch calls/step;
sync total 21.455 s versus 26.145 s before over the same 149 steps. D2H totals
0.969 s versus 0.974 s. Copies are synchronous API wall time, not pure DMA time.
GPU events include event-placement/launch gaps; profiler overhead is present.
Headline throughput uses unprofiled API requests. Earlier direct original
throughput 0.773422 agreed with API 0.774878, excluding API/IPC as the primary
bottleneck. IPC is not independently isolated; host residual includes control,
launching and IPC. No overlapping GPU/wait times are added together.
